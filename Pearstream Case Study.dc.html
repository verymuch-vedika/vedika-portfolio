01

Overview

Problem

Complaints were rising from Web Portal clients, and login, certificate and credential issues were the number one support ticket driver.

Approach

Interviewed the support team, synthesised what they deal with every day, then redesigned login, self-service credentials and admin user management.

Outcome

The redesign is planned to release in parts between November 2026 and February 2027.

02

The problem

The project was triggered by a rise in complaints from Pearstream’s existing Web Portal clients. Within that, my focus was three connected areas: how users log in, how they manage their own credentials, and how support staff step in when something goes wrong.

Web Portal wasn’t a simple login. It was a certificate-based system built for institutional clients in custody and settlement banking, where every client organisation can be configured with different security requirements.

Each client organisation sets its own rules

Factors to sign in
Two or three
First factor
A certificate or a user ID and password
Later steps
Optional, so users can skip ahead, or locked as mandatory

The constraint

The interface had to hold all of these variations in the same small set of screens, without the user ever seeing the configuration logic underneath. Only the right next step.

04 · What I designed

Adaptive multi-factor login

The core login flow had to move on from the legacy method and adapt to each client organisation’s setup: two-factor and three-factor paths through the same screens, with “Try another way” and “Use next verification method” links that only appear when a step is actually optional, and disappear entirely when an organisation has made a factor mandatory.

What we heard

From insight to decision

  1. 01

    Login, certificate and credential issues are the number one ticket driver

    4 of 4 interviews

    What I did

    Rebuilt the login around the failure points support kept describing: certificate import and selection made explicit, expiry surfaced as a status rather than a date to interpret, and every error state given a next step instead of a dead end. Password and authenticator resets moved into self-service, so a five-day manual queue with the support team stops being the only route back in.

  2. 02

    Support can’t grant access; they can only diagnose and redirect

    4 of 4 interviews

    What I did

    Designed for diagnosis as a first-class task: consolidated credential status on the user record, a visible history of who changed what and when, and scoped impersonation so support can see a client’s exact view instead of working from a secondhand description, then hand the action back to the admin who owns it.

  3. 03

    Business users don’t know their own admin is their first point of contact, so they write to support instead

    3 of 4 interviews

    What I did

    Made the admin relationship visible in the product, rather than something a user has to be told. Credential screens name who can act on a request, and the admin’s own user-management views were designed to make that request answerable in a few clicks, so the shortest path is the correct one.

This extended to certificate handling itself: first-time certificate import, choosing between multiple stored certificates, and a “Restart verification” path that warns the user before clearing any progress they’d already made.

Error states were layered too: a wrong password with the number of attempts remaining, a temporary cooldown after too many failed attempts, and a resend limit that pushes the user to another sign-in method rather than a dead end.

05 · What I designed

Self-service credential management

A consolidated “My profile” view brings certificate, password and authenticator app status into one place, each with a clear status tag (active, expiring, expired, blocked or action needed), so a user can see at a glance what needs attention.

From there, users can generate, rename or delete their own certificate, reset their password, and link or unlink an authenticator device, all without raising a support ticket.

A gap I noticed

Designing module by module, as the client wanted, meant no one had traced how one module’s decisions ripple into another’s.

06 · What I designed

Admin user management

Beyond login and credentials, I worked across the full user-lifecycle toolkit admins use to manage other users: creating, modifying, suspending, reactivating, deleting, recovering and duplicating an account.

Each of these seven actions had to support a compliance requirement handed to us. The existing way of approving under both models was inefficient and confusing, forcing a learning curve and a lot of “I’m used to this now”.

2 eyesOne admin

Confirming an action completes it immediately.

4 eyesTwo admins

The same action submits a request. The record shows “Pending”, and a second admin approves or rejects, with a reason required to reject.

Rather than design each action’s approval logic from scratch, we applied that one pattern across all seven. Every action, whichever path it took, is logged to a visible history on the user’s record: who did what, when, and its current status.
